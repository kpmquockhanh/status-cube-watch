# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A desk display for Claude rate-limit usage. Two halves that talk over plain HTTP on the LAN:

- `bridge/` — Go ≥ 1.24, one module dependency (`golang.org/x/text`), built to one binary, `cube-bridge`. Gathers data on the host and serves one small, fully pre-formatted JSON document at `GET /api/status` (plus `/` = browser mock, `/health`).
- `firmware/` — PlatformIO / Arduino for a Waveshare ESP32-S3-Touch-LCD-1.69 (240x280 ST7789V2, CST816 touch), drawn with LovyanGFX (no LVGL) + ArduinoJson. It only polls the bridge (or takes the same payload over BLE) and draws strings; it never talks to Anthropic.
- `mac-helper/` — Swift package building `ClaudeCubeLink.app`: supervises the bridge (a copy of `bridge/` that `build-app.sh` puts in `Contents/Resources/bridge`, the compiled `cube-bridge`, run directly; its settings are kept in the app, edited in "Bridge settings…" and passed to the child as the bridge's env vars, secrets in the Keychain, `BridgeSettings` in `CubeLinkCore`) and pushes `/api/status` to the cube over BLE (CoreBluetooth). Optional; BLE users run its `install.sh` instead of `bridge/agent.sh`. It shows a menu bar item (`StatusMenu.swift`: 5h percent tinted at 60/85%, dropdown of cards, bridge/cube status, Send now / Restart bridge / Cube settings… / Bridge settings… / Forget cube / an "Unlock Mac with cube…" checkbox / Quit, which also stops the bridge child it started); what it displays is derived by the pure `MenuModel` in `CubeLinkCore`.

The README is detailed and authoritative for setup, troubleshooting and design rationale.

## Commands

Bridge (from `bridge/`):
```sh
go build -o cube-bridge ./cmd/cube-bridge && ./cube-bridge   # CUBE_SOURCE=admin ./cube-bridge for the Admin API source
CUBE_EXTRA_CARDS=1 ./cube-bridge     # also include the spend/token cards
go vet ./... && go test ./...        # the bridge's tests (incl. the card-builder golden cases)
./agent.sh install|status|logs|restart|uninstall   # macOS LaunchAgent
```
Config: optional `bridge/config.json` (copy `config.example.json`, gitignored; `cube-bridge` reads `config.json` from the working directory, so run it from `bridge/` or pass `-config <path>`); env vars override it (`CUBE_SOURCE`, `CUBE_PORT`, `CUBE_HOST`, `CUBE_REFRESH_MS`, `CUBE_EXTRA_CARDS`, `ANTHROPIC_ADMIN_KEY`, `ANTHROPIC_ADMIN_OAUTH_TOKEN`). Env booleans override both ways (`CUBE_EXTRA_CARDS=0` beats `extraCards: true`); a bad number falls back to the default with a warning; refresh is at least 1 s. `host` unset = every interface (WiFi cubes need it); `127.0.0.1` is fine for BLE-only. The Mac helper always reads `127.0.0.1`, so a `host` pinned to a LAN address gets a second loopback listener (`internal/server`).

Firmware (from `firmware/`):
```sh
cp src/config.h.example src/config.h  # WiFi + BRIDGE_URL, gitignored
pio run                               # build (also fetches libdeps the simulator needs)
pio run -t upload && pio device monitor
```

Mac helper (from `mac-helper/`):
```sh
swift test                                          # frame encoding, push policy, supervisor decisions, shared fixture
./install.sh install|status|logs|restart|uninstall  # LaunchAgent; install needs a terminal (Bluetooth-permission prompt)
```
`install.sh` builds `cube-bridge` into the app and removes the `bridgeDir` and `nodePath` older installs recorded from the `com.claude-cube.link` defaults, and names `bridge/config.json` in `importConfig`, which the app imports once into its own bridge settings if it has none. Bridge lookup: `CUBE_BRIDGE_DIR`, a leftover `bridgeDir`, the bundled copy, a `bridge/` near the cwd (`swift run`). Edits to `bridge/` reach the installed app only after `./install.sh install`.
App env: `CUBE_PORT`, `CUBE_BRIDGE_DIR` (the directory holding `cube-bridge`); flag `--port`. The bridge-config env vars (`CUBE_SOURCE`, `CUBE_EXTRA_CARDS`, `CUBE_AGENTS`, `CUBE_REFRESH_MS`, `CUBE_HOST`, the admin and Gmail ones) are not passed through to the child: the app's Bridge settings decide them.

Desktop simulator (from `firmware/sim/`, needs `brew install sdl2` and one prior `pio run`):
```sh
make run                                   # SDL window; SCALE=3, CUBE_BRIDGE_URL=... to override
make shot                                  # headless: one PNG per card of the live bridge payload -> build/shot-N.png
./build/cube-shot build/state states.json  # render a saved payload (e.g. red ring, empty track)
./build/cube-shot build/shot @portal       # a screen that is not a payload card: @portal, @ota, @ble-pair|@ble-wait, @unlock|unlock-wait, @waiting, @dev-edit, @agents|agents-scroll, @prompt, @prompt-settle|sent|noanswer|tmux|locked|input|cut|long|wifi|queued|dropped, @vol-56|muted|full|zero|fixed|noout|long|none|press|playing|paused
CUBE_BLE=live|stale|pair|none make run     # what the sim cube believes about Bluetooth (default none); also @ble-pair, @ble-wait shots
CUBE_ORIENT=2 make run                     # sim cube is upside down: flips ~1 s after start (default 0); the window is the only place the flip shows, `make shot` reads back the logical frame and is unaffected
CUBE_BLE=live CUBE_VOLUME=40 make run      # the Volume card with a Mac at 40% (also muted|fixed|none); requests print as [ble] (sim) volume
CUBE_BLE=live CUBE_LOCKED=1 make run       # the Mac is locked: the unlock prompt covers the deck; a tap prints [ble] (sim) unlock (also sets Volume bit 6)
CUBE_PAYLOAD=fixtures/agents-full.json CUBE_BLE=live make run   # serve a saved payload instead of the bridge's; CUBE_PAYLOAD2=<file> CUBE_PAYLOAD2_MS=<ms> swaps to a second one later (an alert); a tap on an answer prints [ble] (sim) answer
make test                                  # host-side unit tests (gesture, deck, portal helpers, ...); no SDL or board needed
make bench                                 # (scenarios: BENCH_RUNS, incl. agents, alert, handover) performance/energy model: real setup()/loop() on a virtual clock, scripted scenarios; fails if a partial push leaves the panel stale, if the screen is still on at the end of `linked` / `sleep`, or if a Settings read over BLE would be stale after an on-device edit (`editor`)
```

There is no linter, and the only automated tests are the host-side unit tests above plus the checks in `make bench`. Verification is: run the bridge, check `/api/status` / the preview page, and use `make shot` to see what the real firmware renderer draws.

## Architecture

**Data flow.** `internal/server` runs a refresh loop: `internal/limits` fetches the two rate-limit windows from `GET https://api.anthropic.com/api/oauth/usage` using the local Claude Code login (macOS Keychain `Claude Code-credentials`, else `~/.claude/.credentials.json`), cached 60s and fail-soft (a failed read keeps the last good one for up to 10 min, then the rings show an empty track and a short reason). Only when `extraCards` is on does it also call a source (`internal/sources/local.go` — incremental byte-offset reader of every `.jsonl` under `~/.claude/projects` (recursive, subagents included; the offset only advances past complete lines; unchanged size+mtime is skipped), dedup on `requestId`, priced via `internal/pricing`; or `internal/sources/admin.go` — Usage & Cost Admin API, refresh floored at 60s). `cards.Build` (`internal/cards`) turns it all into the payload.

**Agents.** On by default (`agents` in `config.json`, or `CUBE_AGENTS`, env wins both ways; `0`/`false` turns it off). Off means no tracker, no AGENTS card, and `/hook` and `/api/answer` answer 404. When on, `internal/agents` (a tracker adapted from agents-deck, provenance in `bridge/internal/agents/NOTICE.md`) follows Claude Code sessions from two inputs: hook events that the bridge's own entries in the global `~/.claude/settings.json` deliver (`cube-bridge hook` reads the event on stdin, POSTs it to `http://127.0.0.1:<port>/hook` with a 300 ms timeout and always exits 0), and discovery of running sessions (`claude agents --json`, at most every 10 s, every 60 s after 10 minutes without an agent, else a process scan; a failed `claude` lookup is retried every 5 min; plus tmux panes on the default server, run with `LC_CTYPE=en_US.UTF-8`, to find a session's pane). The installed hook entry is shared: `agent.sh` and `mac-helper/install.sh` write the same one (the latest install's binary path and port replace the earlier ones), so uninstalling either removes it, and its `--port` is fixed at install time (reinstall after changing the port). `cube-bridge hooks install|uninstall [--port N] [--settings PATH]` edits only its own entries (recognised by command shape), keeps everything else, refuses broken JSON or duplicate keys, writes atomically and keeps a one-time `settings.json.cube-bridge.bak`; `bridge/agent.sh` and `mac-helper/install.sh` run it on install/uninstall (a failure only warns), whatever the flag says. `/api/status` has two variants: the full one (with the prompt `q`) only for a request that passes the **loopback guard** (loopback remote address, `Host` exactly `127.0.0.1:<arrival port>` or `localhost:<arrival port>`, no `Origin`), the LAN variant (tiles only, never prompt text) for everyone else. `POST /hook` and `POST /api/answer` (`{"agent","prompt","key"}`; 204/400/404/405/409/500) need the guard plus the header `X-Cube-Client: 1`. Answering types the key into the agent's tmux pane (an arrow-key menu: arrows from wherever the cursor is now, re-read just before), so only agents in tmux can be answered; the send is not cancelled by the client hanging up, and one that may have typed (timeout) keeps the prompt claimed so a retry answers 409 instead of typing twice.

**Answering from the cube, end to end.** A tap on an answer button sends BLE Control `09` to the Mac app, which POSTs `{agent, prompt, key}` to `127.0.0.1:<port>/api/answer` (`BridgeClient.answer`: header `X-Cube-Client: 1`, 5 s timeout, a fresh ephemeral session per answer, sent once and never retried) and logs one line with the outcome (`answerOutcome`, `describe`); it never tells the cube, which learns from the next payload. The ids pass through unchanged, so the bridge refuses (409) a tap for a prompt that has moved on. `AnswerPolicy` drops an answer, with no request, while the Mac's screen is locked and while another answer is in flight. The Mac sets Volume flag bit 6 (`0x40`) whenever the screen is locked (bit 5, the unlock prompt, stays "Unlock Mac with cube..." on and locked), so the cube greys the buttons first. The app fetches `/api/status` every 1 s while an Agents tile has `k` `wait` and every 5 s otherwise (`PollPolicy`), so a prompt reaches the cube quickly; `PushPolicy`'s 5 s heartbeat is unchanged. Bridge settings has a "Track Claude Code agents (Agents card)" checkbox (`BridgeSettings.agents`, default on, passed to the bridge as `CUBE_AGENTS` 1/0).

**All formatting lives in `bridge/internal/cards`.** Redesigning the dashboard means editing it and rebuilding the bridge — no reflash. Keep it that way: don't add number/unit formatting to the firmware.

**Payload contract** (produced by `internal/cards`, parsed by `firmware/src/payload.cpp` into structs in `payload.h`): `{v, ts, src, cards: [{t, v, s1, s2, c, g?, g2?, c2?, rows?, m?, mc?}]}`. `ts` (build time, epoch s) and `src` (source label) are for people reading the JSON; the firmware ignores them.
- `g` present (0–100) → ring card: `g` fills the arc, `v` goes in the ring center, `s1` captions `v`, `s2` labels the percentage below. `g: -1` = empty track (no reading). No `g` → big-number text card.
- `g2` present (0–100, `-1` = empty track) → dual-ring card, which is what `internal/cards` emits by default (one card, `usageCard`): `g`/`c` are the outer ring (5h), `g2`/`c2` the inner (7d), `v`/`s1` the centre countdown and caption (sized per card, inside the inner ring), `rows` = two `{k, p, r}` legend lines (`drawDualCard` in `ui.cpp`), and `m`/`mc` the unread-mail count + accent, drawn with an envelope in the ring gap (absent = no badge). All optional; a card without `g2` renders as a single ring.
- `a` present (array) → the **Agents card** (`agents.go`, only while the `agents` flag is on; `t` = `AGENTS`, `v` the agent count, `s1` the status caption such as `1 NEEDS YOU`, no `g`): `a` is up to `MaxTiles` = 8 tiles `{i, n, l, k, p, x, u?, h?, s?}` (agent id, name: the session's title, a rename else Claude's own, else the folder, as agents-deck's board names tiles, cut to 16 with `...`; status line, kind `run|wait|idle|err|exit|start`, pose, context used 0-100, `u: 1` = finished a turn nobody looked at, `h` = hat, shape x 8 + colour, 0-103, absent = no hat, see **Theme**; `s` = subagents at work, `""` for one and `"×N"` for more, absent = none). The status line is agents-deck's meta line, made by the bridge: `edit · 41% ctx`, `allow bash?`, `pick 1 of 3`, `hungry · feed me`, `done · 12m ago`, `starting...`, `exited`; its separator `·` (U+00B7) and the `×` (U+00D7) of `s` are the only non-ASCII characters in the payload, both in the firmware's `rm11` font, and `l` is at most 16 characters (`TileLineChars`) and 23 bytes; pose `celebrate` is an agent that finished a turn and was seen less than 6 s ago. Tiles never carry a tool's detail (paths, commands, URLs). `q` is the longest-waiting agent's prompt `{i, p, k, t, d, c, o:[{k,l}], x?, cut?}` (agent id, prompt id, `permission|question|input`, title, detail, context, answer buttons with one-digit keys `1`-`9`, `x: "tmux"` = cannot be answered from here, `cut: 1` = the budget dropped the detail, `d` is then `""`), present only in the full variant (see Agents below); a full-variant Agents card whose `q` the budget dropped carries `qc: 1` instead (the LAN variant never has `qc`). A title or detail longer than its maximum is cut to end in `...` within it. Per-field maxima are the const block in `agents.go` (`TileNameChars` 16, `PromptTitleChars` 40, `PromptDetailChars` 120, `PromptOptions` 6, ...); every `/api/status` body is at most `MaxPayloadBytes` = 2048 (the Mac helper drops anything larger), trimmed in a fixed order: the extra cards (from the end), the prompt detail, options beyond 4, tiles beyond 4, the prompt, the Agents card. The firmware parses `a`/`q`/`qc` into `AgentsData` (see **Agents card** below); the Mac menu bar only recognises the card.
- `c` is an accent name: `accent|blue|green|amber|violet|red` (anything else → ink).
- Firmware limits: `MAX_CARDS = 8`; fixed char buffers (`title`/`value` 24, `sub1`/`sub2` 40, `src` 12) truncate silently. Ring cards share one font size across the deck, sized to the longest `v` inside the ~130px ring center, so keep `v` short.
- Changing the contract means updating `internal/cards` (`cards.go`, and `agents.go` for the Agents card), `payload.h/.cpp`, `ui.cpp`, `preview.html`, and `mac-helper/Sources/CubeLinkCore/MenuModel.swift` (the menu bar parses `t/g/v/s1/s2/rows/m`, and `a` only to recognise the Agents card, and mirrors the 60/85 notches) together.
- The deck is the payload cards, or one "No data yet" card while there are none (`drawWaitingCard`), **plus the Volume card while a Mac is bonded, always last** (`uiDeckSize` / `uiVolumeIndex` in `ui.cpp`; `deckKeepIndex` in `deck_util.h` keeps a viewer on the Volume card as the deck changes). Neither is in the contract or counted against `MAX_CARDS`; boot lands on the first card. The touch gesture classifier (`gesture.cpp`) is pure and host-tested (`make test` in `firmware/sim/`): every tap is a plain `Tap`, delivered as the finger lifts (the editors hit-test it); there are no multi-taps. The Pomodoro timer was removed (October 2026); its BLE Control opcode `04` stays retired, and its NVS keys `pf/ps/pl/pn` are left unread in flash.

**Theme.** The whole cube wears agents-deck's look, except the navigation screens. Palette (tokens at the top of `ui.cpp`): background `#0A0A0A`, panel `#141412`, ink `#E8E4DC`, dim `#7A776F`, line `#262622`, accent `#FF4D00`, empty slot `#0B0B0B`, the Claude chip `#C98B6B`. The payload's accent names keep their spelling and are drawn as `ink` `#E8E4DC`, `accent` `#FF4D00`, `blue` `#6F8FD8`, `green` `#6DBE6A`, `amber` `#E8B94A`, `violet` `#A68BD8`, `red` `#FF4D00` (agents-deck has one alarm colour). Ring tone (`tone()` in `internal/cards`): `ink` below 60 %, `amber` at 60-84 %, `accent` from 85 %. Fonts: Roboto Mono Bold (`rb14`, `rb18`, `rb24`, `rb30`, `rb40`) for titles and values, Share Tech Mono (`rm11`, `rm13`) for small labels and the Agents tiles' names and lines (as agents-deck's board sets them), both generated from `firmware/tools/*.ttf` by `gen_fonts.py` (their OFL texts sit next to them), printable ASCII only; the Inter UI faces are gone from every screen but navigation (the old `b44`, `b36` and `b18` are still generated but nothing draws with them), and the navigation screens keep Inter (`b30`, `b24`, `s12`, `b18v`, `s12v`) and their own colours and look. Panels, tiles, buttons and switches have square corners. The bridge sends captions upper-case and the firmware lower-cases the small labels (`lowerCopy` in `ui.cpp`; `preview.html` does the same with CSS); only `BLE` / `WIFI`, the `OFF` / `OLD` age label and the navigation screens are upper case. The same palette is in `preview.html` (CSS variables; the font stack `"Roboto Mono", "Share Tech Mono", ui-monospace, Menlo, monospace`, no font files served) and in the Mac menu (`MenuModel.tint(percent:)` gives `ink`, `yellow`, `orange` at 60/85, drawn by `tintColor` in `MenuRows.swift`: orange is the palette's #FF4D00, ink is the system text colour (`NSColor.labelColor`) and yellow is #E8B94A in a dark appearance and a darker amber #B07D12 in a light one, so both read on a light menu, and the bar item uses its own text colour for ink). Hats: the bridge picks each folder's hat with agents-deck's `Auto` exactly (`HatOf` in `internal/cards/hats.go`: FNV-1a 32 of the cleaned folder path; shape `v % 13` in the order hard hat, cap, beanie, helmet, wizard, beret, chef, crown, headphones, propeller, top hat, cowboy, bandana; colour `(v >> 8) % 8` in the order teal, blue, yellow, green, purple, pink, sky, ink) and sends it as the tile's `h` = shape x 8 + colour; the firmware only draws it (`hatFromCode` in `critter.cpp`, the art in `hat_art.cpp`). Animation: the critters and the hungry stripes move at 10 frames/s on external power and 2 frames/s on battery (`anim_pacer.h`, `ANIM_EXTERNAL_MS` 100, `ANIM_BATTERY_MS` 500), only while the Agents card or its prompt screen is drawn and the screen is on; the frames are not activity (they never keep the screen awake), and on battery they never raise the CPU to 240 MHz. Whether the cube is on external power is a guess from the cell voltage, since the board has no VBUS or charge pin (`PowerGuess`, `batteryOnExternal()` in `battery_util.h`, host-tested): no cell, or a filtered voltage of at least 4150 mV (`FULL_MV`), or a rise of 20 mV (`RISE_MV`) over the last 120 s (`WINDOW_MS`); a sustained fall (the latest voltage 10 mV, `FALL_MV`, or more under the window's maximum) reads as battery even above 4150 mV and beats that rule (no cell still wins over both). A full cell just unplugged therefore reads as external until the window shows the fall, a couple of minutes. In the simulator and the bench `CUBE_POWER=usb|battery` decides it. `make bench` has `agents-usb` and `agents-battery` (which also runs `agents-battery-still`, the same card drawn still, and fails above 1.2x its MCU mA); with the bench's MCU model that budget can only fail if the CPU leaves 80 MHz on battery: at 80 MHz the model draws 36.1 mA idle and 42.6 mA busy, so even 100% busy is 1.18x, under 1.2x. It does not separate 2 from 10 frames/s, and the model leaves out panel and SPI current, so the real cost of 2 frames/s is for `docs/agents-acceptance.md` to measure (the `batlog` build, `pio run -e batlog`, logs the cell voltage once a minute). Shots: `@agents-hats` (every hat shape, two PNGs) and `@agents-long` (16-character names and lines), next to `@agents`.

**Display panel.** A swipe down on any card (when no editor is open) slides a settings panel in from the top: brightness, screen sleep, auto-advance, sound, same four-row layout (label over value on the left, square `-`/`+` on the right, a stepper that would change nothing drawn disabled) and RESET/DONE bar (geometry in `editor_layout.cpp`; `dev_editor.cpp` owns labels, value text and preset stepping; hit-testing is `devEditorHit`, the layout's `editorHit` plus a Toggle zone; drawn by `uiDeviceEditor`/`uiDeviceSlide`). SLEEP, ADVANCE and SOUND, where 0 means never/off/silent, carry an on/off switch: a tap on the row's left part (`editorLead`) toggles it, their steppers only move between non-zero presets and are inert while off, and turning one back on restores the stored value, else the default, else a preset (15 min / 10 s / MED). Swipe up or DONE closes and saves (`DeviceSettings`, NVS `bl/sl/rt/pi/sd`); brightness previews live, and each SOUND change plays a short beep at the new level. RESET leaves WiFi refresh alone: it has no row here, and the portal and the Mac edit it. Local-only, not in `preview.html`. Preview: `./build/cube-shot build/shot @dev-edit`.

**Volume card.** Shows and sets the Mac's output volume over BLE only. The Mac writes `[1][level|FF][flags][name]` to the Volume characteristic (`volume_frame.h`, pure, host-tested) once it is subscribed and on every CoreAudio change (`SystemVolume.swift`, coalesced 30 ms); the cube asks with Control `05 <level> <muted>`. The card is minimal: name, number and status word in a left column, a slim bar on the right, a tap on the number mutes (`VOL_MUTE_ZONE`), and under both a full-width row of three equal button zones (`VOL_ROW_*`; a touch that lands there is never a drag, so `GestureTracker` stays in tap mode for it) and previous / play-pause / next (tap: Control `06 <key>`, fw_rev 6, which the Mac sends as a MediaRemote command through a one-shot `osascript`, `MediaKeys.swift`: macOS honours MediaRemote only from Apple-signed processes, and this needs no permission) (`drawVolumeCard`; only a vertical drag changes the level, relative to where the finger landed, so a touch or tap never does; geometry and the touch model are `volume_slider.h`, pure, host-tested): on it `GestureTracker::update` runs in drag mode (`dragMode`, 10 px axis lock: vertical = `DragStart`/`Drag`/`DragEnd`, horizontal still swipes), so swipe down does not open the display panel there. While a finger holds the fill and for 600 ms after, states from the Mac are parked (`VOLUME_HOLD_MS`), and requests go at most every 50 ms while dragging, the final value always. States: live, muted, `FIXED` (volume not settable: only mute), `NO OUTPUT`, `NO MAC` (link down: the state is forgotten on disconnect). Volume writes are not readings, so they never keep the screen awake. Local-only, not in `preview.html`. Preview: `./build/cube-shot build/shot @vol-56` (also `muted|full|zero|fixed|noout|long|none|press|playing|paused`; play/pause shows the Mac's Now Playing state, Volume flags bits 3-4, read on the Mac by `NowPlaying.swift` every 250 ms; after a play/pause tap the cube shows the flipped state at once and ignores reports that disagree until one agrees or `VOLUME_PLAY_GUESS_MS`, 1.5 s, passes); in `make run`, `CUBE_BLE=live CUBE_VOLUME=40|muted|fixed`.

**Unlock prompt.** While the Mac's screen is locked and "Unlock Mac with cube…" is on (the login password checked with OpenDirectory and kept in the Keychain, `Unlocker.swift`; lock state from the session's notifications, `ScreenLock.swift`), the Mac sets Volume flag bit 5 and the cube covers the deck with "Tap to unlock" (`uiUnlock`; state machine `unlock_prompt.h`, pure, host-tested). A tap sends Control `07` (fw_rev 7) and shows UNLOCKING until the bit clears or 6 s pass; a swipe shows the deck until 30 s without a touch or the next lock. The Mac types the password and Return as CGEvents (Accessibility permission) only when `UnlockPolicy` (`CubeLinkCore`) agrees: locked, on, trusted, 5 s since the last. The password never goes to the cube. Local-only, not in `preview.html`. Preview: `./build/cube-shot build/shot @unlock` (also `@unlock-wait`); in `make run`, `CUBE_BLE=live CUBE_LOCKED=1`.

**Agents card.** The deck's Agents card (a payload card with `a`, only while the bridge's `agents` flag is on) draws a grid of up to 8 tiles sized by count (one fills the view, two share it at full height, more go two to a row of 108x96, `TILE_W`/`TILE_H`, an odd last one spanning both columns; no empty slots; the critter and text grow with the tile, `tileLook` in `ui.cpp`) under the caption (`s1`, y 44) in a view that scrolls (`agents_layout.h`, pure, host-tested: the same numbers draw and hit-test, `ScrollY` is the drag). A tile is a square panel drawn as agents-deck's board, which is its web app's panel view (`backend/internal/web/static/app.css`, `docs/images/panel-board-v2.png`): the Claude chip (`#C98B6B`) top right; while subagents work (`s`), a 1 px-a-cell critter top left (its body only) and `s` beside it; the critter for its pose (`critter.cpp` and `hat_art.cpp`, a faithful port of agents-deck: 18 x 13 cells of 3 px, alpha-blended, every pose including celebrate, with fades) wearing its hat from `h`; the folder name in 13 px and the bridge's meta line in 11 px Share Tech Mono, each cut with `...` (`drawLine`; the cuts never split a UTF-8 character); and the context as a 2 px gauge round the tile's edge (`drawRing`): a `#2A2925` track, `x` % of it filled in the accent clockwise from the top centre. A waiting tile is filled with the accent with a black critter, text and gauge (on a track of black at 25 %); a hungry tile (idle with `u`, or pose `hungry`) has moving stripes; an exited one sits on the empty-slot colour; an errored one draws an ink critter with an accent meta line; idle, starting and exited ones are dim. `u` draws no dot of its own any more. A vertical drag scrolls only when there are more than 4 tiles and the touch lands on the tiles; otherwise swipe down still opens the display panel. A tap on a waiting tile opens its prompt screen (`uiAgentPrompt`, drawn after the unlock prompt and before the deck): title, the detail in a box, the context, a reason line above the buttons, one button per option (`o`, key in a circle, first one in the accent) and back; a long prompt scrolls. SwipePrev or back close it. `agent_view.h` (`AgentView`, pure, host-tested) decides the screen from the payload it holds and never keeps a pointer into it: `Prompt`, `Queued` ("needs you" / "answer <name> first": the single `q` belongs to another agent), `OverWifi` ("needs you" / "open on Bluetooth": a LAN payload never has `q`), `Dropped` ("too long for the cube" / "answer at the terminal": `qc`), `NoText` ("needs you" / "answer at the terminal"). On `Prompt` the buttons are off, with a reason line, for `input` ("answer at the terminal"), `x: "tmux"` ("not in tmux"), a locked Mac ("unlock Mac first"), the first 1000 ms after the prompt id appeared, after it is drawn again from under another screen (unlock prompt, ride, passkey, a sleeping panel) and after the Mac unlocks (`PROMPT_SETTLE_MS`, `AgentView::resettle`, so a tap aimed at something else cannot land on a prompt nobody has read), and after a tap ("sending..."). A tap sends Control `09 <la> <agent> <lp> <prompt> <key>` (fw_rev 10, `answer_frame.h`, pure, host-tested; Mac link only, one message per tap, never resent) and lights the tapped button; there is one answer per prompt id, remembered across back and reopen, and after `ANSWER_WAIT_MS` (8 s) with no change the line reads "no answer from Mac" and taps work again (so does a send that could not go out, `answerFailed()`). The tap is queued and routed after the pass's payload and Volume intake, and only if the last drawn frame showed the same prompt id and button state, so it can only press what was on screen. Prompt text is drawn only from a payload that arrived over BLE: while BLE is live a WiFi payload is read but not applied. The Volume flag bit 6 says the Mac's screen is locked (set whether or not it will unlock for `07`); the Mac app sets it, and until it does the cube cannot know. The alert (`agent_alert.h`, pure, host-tested): one alert per new prompt id (the last 8 are remembered) or per tile that turns Wait, and a tile that turned Wait just before its prompt arrived is one wait, one beep. An alert wakes the screen (`IdleSleep::wake`), jumps to the Agents card, opens that agent's prompt and plays `Attention`; it is held (and dropped if the agent is answered meanwhile) while a ride, the display panel, a finger on the screen, a BLE passkey, PAIRING OPEN, "waiting for a Mac" or the unlock prompt owns the screen. `readings_key.h` includes the tile ids and kinds, the prompt id and the dropped flag, not the line, pose, context or unseen dot, so those never keep the screen awake. Nothing here is formatted on the cube: every word drawn is the payload's or the fixed copy above. Local-only on the cube; `preview.html` mirrors the grid and the prompt screen, with the buttons always grey ("answer on the cube"). Previews: `./build/cube-shot build/shot @agents` (also `@agents-scroll`) and `@agents-hats`, `@agents-long` and `@prompt` (also `settle|sent|noanswer|tmux|locked|input|cut|long|wifi|queued|dropped`); in `make run`, `CUBE_PAYLOAD`, `CUBE_PAYLOAD2`, `CUBE_PAYLOAD2_MS` (fixtures `agents-full.json`, `agents-lan.json`, `agents-many.json`). `make bench` has `agents`, `alert`, `handover`, `agents-usb` and `agents-battery` scenarios. `docs/agents-acceptance.md` is the open hardware checklist.

**Navigation.** An iPhone app writes map frames to the Nav characteristic (wire format `docs/ble-protocol.md`, decoded by `nav_frame.h`, pure, host-tested; ~5 per second, a `NavScene` of up to 96 streets / 640 points / 256 route points, ~4 KB, so `main.cpp` keeps it in a global). `nav_session.h` (pure, host-tested) decides when the ride owns the screen: a decoded frame starts or keeps it, an Ended frame stops it, 3 s without a frame shows `NO PHONE` (`phoneLost`), 20 s ends the ride by itself, Arrived is shown for 8 s and never starts a ride. While it runs `main.cpp` draws `uiNav` instead of anything else (only a BLE passkey screen outranks it), sets the backlight to 255, keeps the screen on, ignores every gesture but the map's (a drag pans it, `DragMode::Free`; a tap or 8 s without a touch glides it back; `nav_pan.h`, pure, host-tested: the cube sends the offset as Control `08`, the phone builds frames around it and echoes it in a version-2 frame, so the cube draws each frame shifted by its own offset minus the echoed one), freezes rotation and auto-advance and holds the CPU at 240 MHz (the busy scene composes in ~85 ms at 240 MHz and ~250 ms at 80). An open editor is closed without saving when a ride starts; at the end the saved backlight comes back, auto-advance restarts and the deck is where it was. The Volume card and the transport policy follow the Mac's bond only (`bleMacBonded()`); `bleBonded()` (any bond) still gates the first-boot "waiting for a Mac" screen. A boot with the pairing window open shows "PAIRING OPEN" until the window ends, a tap dismisses it or a passkey appears (gestures are ignored while it shows, so nothing reaches the hidden deck). Local-only, not in the payload or `preview.html`. Previews: `./build/cube-shot build/shot @nav-<sample>` (see `shot.cpp`); in `make run`, `CUBE_BLE=live CUBE_NAV=turn` (`CUBE_NAV_STOP_MS`, `CUBE_PAIRING=1`); `CUBE_NAV_PAN=x,y` shoots a dragged map. `make bench` has a `nav` scenario (busy frame every 200 ms). `docs/nav-acceptance.md` is the open hardware checklist.

**Battery indicator.** The top bar of every card shows a battery glyph + percent, read on-device from `PIN_BAT_ADC` (`battery.cpp`; logic in `battery_util.h`, host-tested). It is local-only: not in the payload contract and not in `preview.html`. With no cell fitted (mV < 2500) the cube is on USB and shows a full 100%. On battery the PWR button switches the cube on, and `batteryHoldPower()` (second line of `setup()`) drives SYS_EN (GPIO41, `PIN_SYS_EN`) HIGH so it stays on once PWR is released; there is no power-off in firmware yet. The top bar's right side shows the age of the data (`age_label.h`, pure, host-tested: `OFF` / `Ns` / `Nm` / `Nh` / `OLD`), mirrored in `preview.html`. In the simulator set `CUBE_BATTERY=<0..100>|none` (default 78).

**Screen sleep.** After `SCREEN_SLEEP_MS` (`config.h`, default 15 min, 0 = never) with no touch and no new readings, `main.cpp` turns the backlight off and puts the panel to sleep; a touch wakes it (and is swallowed), data alone does not. New readings means `readingsKey()` changed (`readings_key.h`, pure, host-tested: titles, gauges, mail, text-card values); the Mac's 5 s resend and the ticking countdown do not count, so a cube on a live BLE link still sleeps. Never while the editor is open or a pairing screen is up. Logic is `idle_sleep.h` (pure, host-tested). Local-only, not in the payload or `preview.html`; the sim ignores brightness, so only the state machine is testable off-device.

**CPU clock.** While the screen is on, `cpu_policy.h` (pure, host-tested) runs the CPU at 240 MHz while a finger is down or `uiAnimating()`, and for 1 s after, and at 80 MHz otherwise; with the screen off it is always 80 MHz. APB stays at 80 MHz either way, so SPI/I2C/LEDC timing is unchanged. While animating, `main.cpp` paces each pass to `FRAME_MS` (16 ms) instead of spinning. `make bench` (`sim/bench.cpp`, `bench_panel.h`) is the model behind these choices: it runs the real `setup()`/`loop()` against scripted touch/BLE/WiFi and a counting panel, and estimates MCU current from the ESP32-S3 datasheet; radio, backlight LED and panel current are not modelled. Touch is read over I2C only when it can matter (`touch_gate.h`, pure, host-tested): after the CST816 pulls INT low, on every pass while a finger is down, and every 250 ms otherwise; and only once INT has announced a landing finger, so until then, or after it misses one, every pass reads as before. There is no light sleep between passes: automatic light sleep needs `CONFIG_PM_ENABLE` (and BT controller modem sleep), which the prebuilt Arduino core's sdkconfig leaves off, so it would take a custom-built core; `delay()` already idles the CPU at 80 MHz.

**Auto-rotate.** The cube flips its display 180° when stood on its other end, always on (no setting). `imu.cpp` reads the QMI8658C accelerometer (I2C `0x6B`, shared bus) and `main.cpp` polls it at 5 Hz into `Orientation` (`orientation.h`, pure, host-tested: `|up| > 0.6 g`, `|up| > |az|`, held 1 s, deferred while a finger is down; flat or tilted never flips). The result goes to `lcd.setRotation(0|2)`, so `ui.cpp` and `preview.html` are untouched; raw CST816 coordinates are mirrored by `touchToScreen` (`touch_map.h`) before gesture code sees them. The panel is not written while the screen sleeps; the rotation is applied on wake before the first frame. Local-only: not in the payload contract. `IMU_UP_SIGN` in `board_pins.h` is the sign of IMU X when the screen top is up (X is the vertical axis with the cube on its edge, measured; the sign is still to be confirmed on hardware); `docs/imu-acceptance.md` is the open checklist. The simulator stand-in is `imu_sim.cpp` (`CUBE_ORIENT`); `touch_sim.cpp` undoes the mirror so `main.cpp` sees raw coordinates as on the board.

**Buzzer.** The passive buzzer on GPIO42 (`PIN_BUZZER`, `board_pins.h`) plays only the `Preview` beep for now, when SOUND changes in the display panel. `Attention` plays when the Agents alert fires (an agent has a new prompt, see **Agents card**). `buzzerBegin()` is the first line of `setup()` and drives the pin LOW, because a floating buzzer pin heats the 3.3 V LDO. The tone uses LEDC channel 0 (timer 0), away from the backlight's channel 7 on timer 3; `tone()` is not used.

The tunes and their timing are `melody.h` (`MelodyPlayer`, pure, host-tested). Timing starts at the first `update()` after `play()`, and a late pass skips ahead, so a tune keeps its length. `buzzer.cpp` only turns the pitch that `update()` returns into LEDC writes, and `buzzerUpdate(now)` runs every pass.

The level is `DeviceSettings.sound`: 0 off, 1 LOW, 2 MED, 3 HIGH. It is stored under NVS and BLE key `sd` (BLE from fw_rev 4), and defaults to `BUZZER_LEVEL` = 2. Each level is a duty cycle tuned by ear (`DUTY` in `buzzer.cpp`). The Mac's settings window shows Sound only when the cube reports `sd`. Local-only: not in the payload or `preview.html`. The simulator only logs `[buzz] <sound> @<level>`. `docs/buzzer-acceptance.md` is the open hardware checklist.

**Three renderers of the same layout.**
- `firmware/src/ui.cpp` — the real one: whole frame composed in one full-screen sprite, then `present()` sends only the rows whose hash changed since the last frame (FNV-1a over 32-bit words with a shift folded in after each step: with a plain multiply, changes in the high bits of two words could cancel and leave critter rows stale, which `make bench` caught) (a full frame on rotation change, after `uiInvalidate()` on wake, and once a minute). Every screen function ends in `present(lcd)`; nothing writes to the panel directly. Ring notches at 60%/85% (`NOTCHES`), animations (700ms first sweep, 260ms retarget, 400ms colour crossfade); `uiAnimating()` tells `main.cpp` to keep drawing frames.
- `bridge/preview.html` — a separate JS/SVG reimplementation for browser previewing; it shows whether the data reads well, not whether the firmware draws it correctly. Layout/threshold changes in `ui.cpp` must be mirrored here by hand.
- `firmware/sim/` — compiles the real `main.cpp`, `ui.cpp`, `payload.cpp` against LovyanGFX's SDL backend (`-DLGFX_SDL`). Only hardware layers are swapped: `net_sim.cpp` (socket HTTP GET, on a thread) for `net.cpp`, `touch_sim.cpp` (mouse) for `touch.cpp`, and `sim/Arduino.h` is a tiny shim (millis/delay/Serial/min/max/constrain). Firmware code shared with the sim must stay within that shim; `display.h` has an `#ifdef LGFX_SDL` branch for the sim panel.

**Transports.** The cube takes the same payload over BLE (preferred) or WiFi polling. BLE: `net_ble.cpp` is a NimBLE GATT server (Payload write / Control notify / Info read / Nav write, passkey pairing; a Mac and an iPhone bonded and connected at once, fw_rev 8; who may stay connected is `ble_bonds.h`, pure, host-tested: Just Works links, a new bond outside the 120 s pairing window that the portal's "Pair new device" opens at the next boot (NVS `ble/pw`), and a link not secured within 60 s (`bleUnsecuredExpired`) are dropped; a bond's kind (Mac / iPhone, NVS `ble/<address>`) is learned from its first write, Nav = iPhone, and replaces an older bond of that kind (`bleBondToEvict`); once secured it asks the Mac for a 30–45 ms interval with peripheral latency 6, `BLE_IDLE_PARAMS`, and the iPhone for 15–30 ms with no latency, `BLE_NAV_PARAMS`, both in `ble_conn.h`, checked against Apple's rules by a `static_assert` and a host test; `bleTakeNav()` hands the latest decoded `NavScene` to the loop, and a coordinate outside x [-64, 304], y [-64, 344] rejects the frame, `nav_frame.h`; it advertises only while a bonded device is not connected, or with no bond, or during the pairing window (`bleShouldAdvertise`), and shows a passkey only for a pairing that can be accepted (`bleShowPasskey`)); `ble_frame.h` (`FrameAssembler`) reassembles chunked JSON and `bleTake()` feeds it to the unchanged `payloadFromJson()`. `transport_policy.h` (pure, host-tested) decides when WiFi runs: off while a BLE payload arrived in the last 15 s, on when it goes stale (or there is no Mac bond), off again after 30 s of steady BLE, and always off while a ride runs (one 2.4 GHz radio, shared with the phone's link) unless `WIFI_ALWAYS_ON`. The WiFi GET runs on a FreeRTOS task of `net.cpp` (`netRequest()` starts it, `netTake()` hands the result to the loop), so a bridge that is down or a DNS lookup that hangs never stalls touch or animation; `WIFI_ALWAYS_ON` (`config.h`) keeps it up for OTA. Boot no longer forces the setup portal when there is no SSID; WiFi is joined at boot only with neither a Mac nor an iPhone bonded, and the portal auto-opens on a failed join only with no bond of any kind (`bootWifiPlan`), so a phone-only cube away from its network still reaches the deck; "Pair new device", "Forget Mac" and "Forget iPhone" (`bleRequestPairingAtBoot()`, `bleForget()`) live in the portal. The wire format is `docs/ble-protocol.md`, pinned by `firmware/sim/fixtures/ble-frames.txt`, which both `make test` and `swift test` read. The Settings characteristic (`settings_json.cpp`, host-tested; `CubeSettings.swift` on the Mac, edited via the menu's "Cube settings…" window) lets the Mac change everything the portal can, over the same encrypted link; only the groups that changed are written, network last (`Ok` can mean a partial save, so the Mac reads back), and a rejected write is republished so a read never returns it; see the protocol doc. Control `05 <level> <muted>` (cube -> Mac) and the Volume characteristic (Mac -> cube, fw_rev 5) carry the Volume card. The Mac side is `mac-helper/` (`BridgeSupervisor` runs the `cube-bridge` binary or adopts one already serving the port, `CubeLink` is CoreBluetooth, `PushPolicy` sends on change / every 5 s / on "send now" and never when the bridge is down). The top bar shows which transport delivered the data (`BLE` or `WIFI`, `UiLink` passed to `uiRender`; blank when offline); like the battery it is local-only, not in the payload and not in `preview.html`. In the simulator `ble_sim.cpp` stands in for `net_ble.cpp` (`CUBE_BLE`; `CUBE_NAV=<sample>` is an iPhone sending a `nav_samples.h` frame every 200 ms, `CUBE_NAV_STOP_MS` stops it, `CUBE_PAIRING=1` opens the pairing window) and `CUBE_LINK=ble|wifi|none` picks the marker in `make shot`. The BLE path has not been run on a real cube; `docs/ble-acceptance.md` is the open checklist.

**Hardware specifics** are isolated in `firmware/src/board_pins.h` (all pins, `LCD_OFFSET_Y`) and `firmware/src/display.h` (LovyanGFX panel config, `cfg.invert`). Board reference (peripherals, full GPIO map, I2C addresses) is in `docs/ESP32-S3-Touch-LCD-1.69.md`.

**Settings, portal and OTA.** The portal form also edits display/behaviour knobs (`DeviceSettings` in `device_settings.h`: backlight, screen-sleep minutes, auto-advance seconds, WiFi poll seconds, buzzer level; NVS keys `bl/sl/rt/pi/sd`, defaults from the old `config.h` macros via `device_defaults.h`); a blank numeric field keeps the current value. WiFi SSID/password, bridge URL and OTA password live in NVS (`settings.cpp`, namespace `cube`), falling back to `config.h` for any key never stored, so an empty NVS behaves exactly like before. The setup portal (`portal.cpp`: SoftAP `claude-cube-XXXX` + DNS catch-all + one form at 192.168.71.1, not .4.1 so the station side can join a 192.168.4.x LAN) starts when the screen is touched in the 3 s boot window (`SETUP_WINDOW_MS`) and held for 5 s, or when the boot WiFi join fails for ~20 s and no device of any kind is bonded. It runs AP+STA: while nobody is on the AP it retries the stored network (10 s every 30 s); once joined it shows the LAN address and serves the form there too. Every request must name the cube by address and every save/forget carry a per-boot token (`portalHostIs` / `portalTokenOk` in `portal_util.h`, host-tested), so other web pages cannot post to it. Opened by a failed join (`autoRetry`), it reboots to normal as soon as the stored network answers (`portalStaRecoveredReboot`); there is no idle reboot. A blank OTA password keeps the stored one; a checkbox clears it. With no SSID and no bond the cube shows "Waiting for a Mac" instead (a touch dismisses it). OTA is ArduinoOTA as `claude-cube.local` (see the commented `upload_protocol = espota` lines in `platformio.ini`). `settings.cpp`, `portal.cpp` and `ota.cpp` are hardware-only and have stand-ins in `firmware/sim/`.
